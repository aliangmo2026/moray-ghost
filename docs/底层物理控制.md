# 底层物理控制：三个用真机换来的一线踩坑经验

> 来源：moray-ghost v0.9「纯鼠标绘画」攻坚（2026-10-26）。我们让一个本地 AI 服务
> 用**真实鼠标**在 Win11 画图里画出了一只鲸鱼（`scripts/test_v09_draw_whale.py`，
> 25/25，7658 笔迹像素/8 独立元素）。过程中在**物理输入层**连撞三个坑——每个坑
> 的症状都极具迷惑性（"我的自动化代码明明是对的"），根因却全在操作系统层。
> 这份文档写给所有做桌面自动化（RPA / GUI Agent / 输入注入）的人。

## 陷阱一：SetCursorPos 不触发轨迹——现代画图应用只认真实鼠标事件

### 现象

`pyautogui.moveTo` / `SetCursorPos` 移动光标 + `mouseDown/mouseUp`，在记事本、
浏览器、常规 Win32 程序里"拖拽"一切正常；但在 **Win11 画图（WinUI 3 / 指针输入
应用）**里，无论轨迹点给多少个、多么平滑，画出来的永远是
**起点→终点的一条直线**。多段曲线变成几条直线——鲸鱼直接变成"几笔折线"。

### 根因

- `SetCursorPos` 是**瞬移**：直接改光标坐标，**不生成 WM_MOUSEMOVE 事件流**。
  靠 `GetCursorPos` 轮询的代码看着一切正常，但应用收不到"移动事件"。
- 传统应用（Win32/大多数软件）在 mouseDown/mouseUp 之间会用当前光标位置补线，
  所以"看起来能拖"。
- **现代指针输入应用（WinUI 画图、OneNote、Whiteboard 类）只把真正的鼠标移动
  事件画进墨迹**——没有事件流，就没有笔迹。这是性能与延迟优化的正当设计，
  但对注入式自动化是致命的。

### 修复

绝对坐标的**真实鼠标移动事件**（`mouse_event` + `MOUSEEVENTF_ABSOLUTE`）：

```python
_MOUSEEVENTF_MOVE = 0x0001
_MOUSEEVENTF_ABSOLUTE = 0x8000
_MOUSEEVENTF_VIRTUALDESK = 0x4000

def _mouse_event_absolute(x: int, y: int) -> None:
    xv = user32.GetSystemMetrics(76)   # SM_XVIRTUALSCREEN
    yv = user32.GetSystemMetrics(77)   # SM_YVIRTUALSCREEN
    wv = user32.GetSystemMetrics(78)   # SM_CXVIRTUALSCREEN
    hv = user32.GetSystemMetrics(79)   # SM_CYVIRTUALSCREEN
    nx = int(round((x - xv) * 65535.0 / max(1, wv - 1)))   # 归一化 0..65535
    ny = int(round((y - yv) * 65535.0 / max(1, hv - 1)))
    user32.mouse_event(_MOUSEEVENTF_MOVE | _MOUSEEVENTF_ABSOLUTE
                       | _MOUSEEVENTF_VIRTUALDESK, nx, ny, 0, 0)
```

要点：
- **归一化到 0..65535** 是按**虚拟桌面**（`VIRTUALDESK`）而非单显示器——多屏
  与负坐标副屏才不会错位；
- `mouseDown` 之后**逐点发 MOVE 事件**（我们的 `backend.move_to` 已整体切换到
  该路径，`pyautogui.moveTo` 只留作落点校验失败时的兜底）；
- `SendInput` 也能做同样的事，且更原子；`mouse_event` 是老 API 但兼容性最好。
  二者都比 `SetCursorPos` 强——**判断标准是"应用能不能看到移动事件流"**。

### 自检方法

在目标应用里手动画一笔，用注入代码重放同一条轨迹，截图做像素差分：
真事件 → 笔迹与手画一致；`SetCursorPos` → 一条直线。我们的画图验收
（`test_v08_paint_precision.py`）用同样思路做像素级 bbox 比对，逐边误差 2-4px。

## 陷阱二：ctypes 签名污染——拿共享 user32 句柄设签名，毒死 pyautogui

### 现象

为了让鼠标事件走真实移动（陷阱一），很自然地写下：

```python
ctypes.windll.user32.mouse_event.argtypes = (c_uint, c_uint, c_uint, c_uint, c_ulong)
```

然后**其他毫不相关的代码开始爆炸**：`pyautogui.mouseDown()` 抛
`ArgumentError: argument 1: TypeError: wrong type`（c_long 报错），
而且报错位置在 pyautogui 内部——你改的是自己的 `mouse_event`，关它什么事？

### 根因

`ctypes.windll.user32` 是一个**全局共享的 DLL 句柄缓存**：windll 工厂对同一个
DLL 在进程内只造一个对象，其上的每个导出函数（`mouse_event`、`GetCursorPos`…）
的 `argtypes/restype` 也是**进程级单例**。pyautogui 内部同样走
`ctypes.windll.user32`——你给自己的 `mouse_event` 设的签名，就是 pyautogui 用
的同一个函数指针。更隐蔽的是：如果签名恰好"能凑合"，污染会以**静默数据截断**
的形式存在——比如把 64 位句柄（HKL、HICON）放进默认 c_int（32 位）参数，
高位被无声砍掉，功能"时灵时不灵"。

### 修复

**私有 DLL 句柄**：所有需要自定义签名的 win32 调用一律用独立实例，
不碰 `ctypes.windll` 缓存：

```python
# 私有句柄：只给本模块的 mouse_event 设签名，绝不污染
# ctypes.windll.user32 上 pyautogui 共用的函数指针
_USER32 = ctypes.WinDLL("user32", use_last_error=True)
_MOUSE_EVENT = _USER32.mouse_event
_MOUSE_EVENT.argtypes = (ctypes.c_uint,) * 4 + (ctypes.c_ulong,)
_MOUSE_EVENT.restype = None
```

### 举一反三（同类坑）

- 任何"改 argtypes/restype"的操作，先问一句：**这个 DLL 句柄是不是别的库也在
  用？**（pyautogui、pywin32、keyboard 都可能共享 windll 缓存）
- 64 位句柄类型必须显式 `c_void_p` 并设 argtypes/restype——本机中文 IME 排查
  时，`ActivateKeyboardLayout` 的 HKL 句柄就因为缺省类型被静默截断，
  "切了没效果"，设成 `c_void_p` 后立即恢复正常；
- 排查招法：报错栈在**第三方库内部** + 你最近动过 ctypes 签名 = 先怀疑污染。
  把你的签名撤掉看它是否痊愈，痊愈即坐实。

## 陷阱三：画图软件会"合并"闭合线——轨迹设计要主动留缺口

### 现象（三个连环）

在画图里做笔迹绘制/验证时：

1. **首尾相接的轨迹被并成闭合形状**：轨迹起点=终点的圆形/心形一笔画，
   应用把它当闭合轮廓处理——后续填充、选中、橡皮的行为都和"开放线"不同；
2. **填充桶（B 键）会从任何缺口泄漏**：想用粗笔刷选了 B，结果它是
   填充工具——画布有任何一条没封口的线，填充就漏出去把**整张画布填黑**；
3. **相触的笔画在验证层合并**：两条贴近的笔迹（如双线加粗、补缺口）会融合成
   一个连通域——用连通域数量做"画了几个元素"的像素验证时，计数会**少于**
   实际笔画数，误判成"漏画"。

### 实证（鲸鱼脚本里的防御姿势）

`scripts/test_v09_draw_whale.py` 的每一条轨迹都是**刻意开放**的：

```python
eye   = chaikin(circle_points(cx, cy, r)[:22], 2, closed=False)   # 28 个点只取 22 个
heart = chaikin(heart_points(cx, cy, s)[:38], 1, closed=False)    # 48 个点只取 38 个
# Chaikin closed=False 时首尾之间天然留一段缺口（不回补起点）
```

- **画开放图形**：圆形截 ~78% 弧长，首尾留 60-80° 缺口；
- **加粗不用填充**：主体用"同轨迹偏移 1px 画第二遍"的双线加粗，绕开填充桶；
- **验证按像素不按笔画数**：`cv2.absdiff` 像素差分定笔迹存在，
  连通域数量只做 **下界断言**（≥N 而非 ==N），相触合并不误伤；
- **颜色取自色板**：不赌调色板布局，CV 在窗口顶部色板区找"实心纯色圆点"
  （HSV 域 + 填充率 ≥0.35 排除选中态空心环 + 中心像素复核），
  该逻辑已沉淀为通用接口 `POST /api/ghost/draw_trajectory` 的 `color` 参数。

### 通用规则

- 想要"开放曲线"，**永远主动留缺口**，不要让轨迹首尾重合；
- 想要"闭合形状"，明确接受"应用会把它当形状对待"的语义（填充/选中会整块走）；
- 自动化验证一律以**像素证据**为准：差分像素数、bbox、颜色直方图；
  笔画数只能当下界。

## 附：两个相邻的物理层坑（一句话版）

- **pyautogui.PAUSE 是逐次施加的**：默认 0.05s 挂在*每一次* API 调用上，
  逐点轨迹循环会累积（375 点 ≈ 19s 纯死等）。多点循环期间 `PAUSE=0`，
  finally 还原。
- **pyautogui 的 Fail-Safe 是四个角不是左上角**：
  `FAILSAFE_POINTS = [(0,0), (0,h-1), (w-1,0), (w-1,h-1)]`——用户把鼠标停在
  **任意**角落都会中止你的自动化（409 FAIL_SAFE_TRIGGERED）。跑批量任务前先
  `GetCursorPos` 看一眼四角。自己用 `mouse_event` 绕过了 pyautogui 调用级
  Fail-Safe 时，记得**手动补回逐点四角检查**（我们保存了该语义）。
